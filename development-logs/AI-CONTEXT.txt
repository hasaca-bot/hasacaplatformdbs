# PROJECT SUMMARY
HASACA is a production-grade, white-label, MULTI-TENANT SaaS restaurant platform. One codebase
serves many restaurants ("tenants"); each gets a public website, a tenant admin panel, QR table
ordering, delivery/dine-in ordering, reservations, and push notifications. A Root (super-admin)
Panel manages all tenants. As of Phase 22 there is ALSO a public marketing site for HASACA itself.

- Tech stack: Node.js + Express (no framework beyond Express). Dual DB layer: SQLite (dev, via
  Node built-in `node:sqlite`) OR PostgreSQL (prod, `pg`) chosen by `DATABASE_URL`. Frontend = FOUR
  static HTML pages, NO bundler, NO React — each page has its own embedded `<style>` and `<script>`
  and an inline `i18nData` object. `web-push` for notifications, `qrcode` for QR.

# KNOWN ISSUES
- NAMING TRAP in index.html's theme classes: `body.theme-bw` is the LIGHT theme (warm accents
  intentional); `body.theme-mono` is the actual black & white theme. Several older notes in this file
  called `theme-bw` the B&W theme — wrong, corrected during P31's research. Read the class, not the name.
- RESOLVED (P32): B&W theme (`theme-mono`) is now verified genuinely orange-free — 0 warm computed-
  style hits (was 106), confirmed via fresh-navigation-per-theme scans (not runtime `applyTheme()`
  switches — see the next bullet for why that distinction matters). The ".pax-btn keeps warm accents"
  claim that used to live here was already stale before P32 even started (fixed back in P25.2).
- CSS custom-property "used value" staleness after a RUNTIME class change, in THIS preview pane
  specifically, when `document.visibilityState==='hidden'` (i.e. the pane isn't composited/visible).
  Extends the already-known "CSS transitions freeze when hidden" limitation: some derived styles
  (box-shadow and other `var()`-driven properties) don't get recomputed after `classList` changes made
  after the tab's initial paint, even though simpler custom-property lookups DO update correctly. Not a
  code bug — proven during P32 by comparing `applyTheme('bw')` (stale, wrong) against
  `localStorage.theme='bw'` + a fresh navigation (correct) on the exact same elements. WORKAROUND: when
  verifying theme-dependent styles in this environment, always set the theme via `localStorage` BEFORE
  navigating, never switch themes at runtime and read computed styles in the same session afterward.
- admin.html "Bildirim Gönder" tab label is TR-only (no EN i18n).
- Preview-tab CSS transitions freeze when `document.visibilityState === 'hidden'`, so reveal/float
  animations cannot be screenshotted in this environment — verify them via DOM assertions instead.
- Landing stats/testimonials/pricing are placeholder marketing content, not real figures.
- A leftover second tenant (from tests) may exist in the dev DB; harmless.

# IMPORTANT DESIGN DECISIONS  (+ WHY)
- Static HTML pages, no bundler/React → WHY: pre-existing architecture; keep zero build step,
  deployable as static + one Express server. Do NOT introduce a frontend framework.
- Dual SQLite/Postgres via isPg + param duality → WHY: cheap local dev + prod with one codebase.
  Always write portable SQL or aggregate in JS.
- Master-template CLONE model (`default` = "My Restaurant") → WHY: new tenants are never empty.
- Tenant text stored in DB `translations` (overrides static i18nData) → WHY: per-tenant customization
  without code changes. Lesson: to change visible text you must update the DB rows, not only the HTML.
- Uploads stored as FILES + URL in DB (never base64) → WHY: keeps DB/pages small; images cacheable.
- Same-origin RELATIVE upload URLs → WHY: work across custom domains/subdomains without hardcoding host.
- Delete-then-regenerate `default` → WHY: platform must never be tenant-less.
- Health/Activity/Analytics read ONLY app-available info → WHY: must run on any cloud host with no
  provider APIs.
- robots.txt / sitemap.xml generated per-request from `req.headers.host` → WHY: one deployment serves
  many tenant subdomains/custom domains; a static file would hardcode one domain (it previously leaked
  `dayikatik.netlify.app`).
- Global font via ONE universal `*{font-family:var(--font-primary)!important}` rule per page → WHY:
  user required the font on EVERY element and forbade per-component assignment.
- PWA install disabled behind ENABLE_PWA → WHY: behave as a normal responsive site now; one-flag re-enable.
- [P22] Landing served at `/landing`, NOT `/` → WHY: `/` must keep serving the tenant restaurant site;
  tenant resolution and every existing route stay untouched. Apex-domain routing is a deploy concern.
- [P22] Landing visuals are CSS + inline SVG, zero external assets → WHY: no CDN/CSP risk, no image
  payload, instantly themeable, and it renders identically offline — the Stripe/Linear approach of
  crafting UI rather than shipping screenshots.
- [P22] `landing_messages` is platform-level (no tenant_id) → WHY: these are HASACA's own sales leads,
  not a tenant's data; making them tenant-scoped would be semantically wrong and leak-prone.
- [P22] Reveal animations gated behind `.js-anim` + safety timeout → WHY: content must never be
  permanently invisible if JS fails; a marketing page that renders blank is worse than an unanimated one.
- [P23] ONE registry (`marketing-data.js`) + ONE shell (`marketing.html`) instead of 45 HTML files →
  WHY: 45 copies would fork the design system 45 ways and make any change a 45-file edit. Adding a
  page is now a single registry entry that automatically gains a route, footer slot, sitemap entry
  and SEO meta. NEVER hardcode a marketing link list — read it from MARKETING.pages.
- [P23] Marketing meta injected SERVER-side into `<!--HEAD-->` → WHY: client-rendered titles are not
  reliably crawlable; each URL must ship its own real title/description/canonical/OG.
- [P23] The 4 marketing forms reuse `POST /api/landing/contact` and tag the lead in its message
  (`[Demo Talebi]` etc.) → WHY: keeps every lead in ONE Root inbox with zero schema change.
- [P23] Login page writes to `sessionStorage` when "Beni hatırla" is off → the panels' token getters
  were extended to fall back to sessionStorage. This is SESSION PERSISTENCE, not auth logic: token
  issuing/validation is untouched. Do not "simplify" the getters back to localStorage-only — that
  silently breaks login whenever Remember Me is unchecked.
- [P24] ONE shared `panel.css` (not per-page inline) for the panel design system → WHY: it is the
  "centralized design tokens" the spec asked for and lets admin.html reuse the exact same themes next
  phase. Linked LAST in <head> so it overrides inline rules; keeps existing var names so legacy CSS
  re-themes automatically. No hardcoded colors outside the token `:root`/`[data-theme]` blocks.
- [P24] Sidebar items reuse the EXISTING modal openers instead of converting modals to routed views →
  WHY: the spec says "reuse existing JS, do not rewrite." Only Dashboard + Restaurants are inline
  views; Health/Activity/Analytics/Notify/Landing/Brand/AI stay as (restyled) modals. Zero logic risk.
- [P24] Theme persisted in localStorage['hasaca_panel_theme'] and applied as `data-theme` on <html> →
  WHY: shared across root.html, admin.html and login.html for one consistent panel theme.
- [P25] admin.html did NOT link panel.css and does NOT reuse :root token names → WHY: admin.html IS the
  customer restaurant page + an overlay; its :root defines --fire/--card/--dark/etc for the CUSTOMER
  hero/menu, and panel.css reuses those names → linking it would repaint the live customer site on load.
  Instead the overlay gets a self-contained, uniquely-named `--ap-*` token block scoped to
  `#adminPanelOverlay` (+ `html[data-theme=light] #adminPanelOverlay` for light). The per-tab --ord-*/
  --tbl-* families (normally gated by body.theme-bw) are remapped to --ap-* so the panel follows the
  panel theme, not the customer theme. NEVER touch the customer :root tokens or body.theme-bw here.
- [P25 revised] The sidebar shell CSS is a LOCAL port of panel.css's shell rules, every selector
  prefixed with `#adminPanelOverlay` and reading --ap-* — for the same reason. Root.html's shell
  DOM/class names (`.app-shell/.app-sidebar/.nav-group/.nav-item/.app-topbar/.app-content/.dash-grid/
  .stat-card/.panel-card/.act-row/.profile*`) are reused so both panels stay visually identical.
- [P25 revised] The sidebar deliberately SHIPS ONLY items with backing functionality → no dead links.
  Anything requiring new tables/endpoints (Müşteriler, Raporlar, AI, Kullanıcılar, Profil, tenant
  Restoran Ayarları, tenant İletişim Mesajları) is OMITTED not faked, since a UI-only phase can't add
  business logic without violating the "do not touch" rule. Documented as backlog above.
- [P27 Part A] Relocated the two forms via a JS IIFE (`appendChild` + add `.view` + `hidden=true`) at
  page-load instead of physically cutting/pasting ~240 lines of HTML → WHY: produces an IDENTICAL
  live-DOM result with a far smaller, safer diff — the explicit ask that phase was to minimize edits.
- [P27 Part B] "Plan then execute", never direct-write → WHY: the AI must never silently mutate data;
  the admin previews every field-level change and must Confirm before anything is written. Plans are
  cached IN-MEMORY only (a plain Map, never a DB table) and are single-use + short-TTL + scoped to the
  exact caller (tenant_id match, or a root-only cache) — this cache IS the tenant-isolation boundary
  for this feature, enforced the same way every other route enforces it.
- [P27 Part B] AI writes ONLY through a per-caller FIELD WHITELIST, reusing the exact update statement
  the manual REST handler already uses (never a new/parallel mutation path) → WHY: your explicit rule
  was "the AI must only modify values that are already editable" and "do not create a new backend
  architecture." Anything outside the whitelist is returned in `unsupported`, never faked.
- [P27 Part B] Root's assistant is scoped to ALLOWED_PLATFORM_KEYS only, NOT a specific tenant's
  menu/branding → WHY: editing another tenant's data would need a tenant-selector UI and meaningfully
  widens blast radius; deliberately deferred as a fast-follow rather than built into this pass.
- [P28] Widget flags live INSIDE the existing `settings` JSON blob (`settings.widgets`), not a new
  column → WHY: zero migration, and `GET /api/site-config` already passes `settings` through as-is, so

## Contrast-checking method (Phase 37)
When investigating a color-legibility complaint, don't read CSS by eye — inject a live-DOM contrast
checker (walk every visible text node, compute actual `getComputedStyle` color vs. the nearest
opaque ancestor background, flag ratios below ~4.5:1 for normal text / 3:1 for large-bold) and run it
across every view/theme. It reliably finds real bugs (found `root.html`'s duplicate `.chip.active`
rule this way — near-black text on a near-black background, ratio 1.0) but has a real blind spot:
it can't read `background-image` gradients, so it walks past them to a distant ancestor and produces
false positives. Always verify a hit with a direct `getComputedStyle(el).backgroundImage` check (or
just a screenshot) before treating it as real — several flagged items this phase turned out to be
perfectly legible gradient buttons the checker simply couldn't see.
